# Architecture

Mallside is a static browser application. `dist/` contains the editable HTML, CSS and ES modules as well as the deployable assets. It is not generated by an untracked build. Node's standard library runs tests and release checks; Python's standard library provides the development server. The same-repository Pages workflow uses pinned esbuild to create a minified production artifact; see DEPLOYMENT.md.

| Area | Main modules |
| --- | --- |
| Page structure, controls and view lifecycle | `index.html`, `app.js`, `styles.css`, `life-styles.css` |
| State, economy, needs, progression, inventory and persistence normalization | `engine.js`, `mall-life.js`, `community-stories.js`, `neighborhood-life.js`, `home-life.js`, `trip-planner.js`, `journey.js` |
| Store/product identity, branch stock and provenance | `catalog.js`, `playable-stores.js`, `retailer-evidence-v12.js`, `store-product-seeds.js`, `product-photos.js` |

| 3D scene and store activity | `world-3d.js`, `shop-interiors.js`, `store-fitout.js`, `store-life.js`, `store-customers.js` |

The runtime uses vendored Three.js r180. Bundled relative asset/module URLs let the same `dist/` run at `/` or the GitHub Pages `/Mallside/` prefix. Do not introduce origin-root `/assets/...` or `/app.js` paths. Module version query strings are cache keys, not a mandatory deployment version schema. The GitHub migration changes packaging metadata and adds rights links in the menu/footer. The v28 UI entry uses `app.js?v=29.0.0`; changed module imports share their new cache keys while unchanged modules retain earlier keys. The production artifact bundles these into one content-hashed script.

## State and saves

The UI owns a normalized engine state and remembers unpaid selections before saving. Browser local storage holds career and free-shop saves separately. Returns use game receipts and game rules; no real merchandise purchase or refund occurs. State changes should go through the engine functions and maintain their tested invariants. A paid purchase should not be duplicated by reloading, and ambient NPC shopping must not alter player money or stock.

Primary keys remain `mallside-career` and `mallside-free`, containing the original version-6 JSON. `engine.parseSave` validates critical progression before using the existing migrations (versions 1–6); strict normalization throws instead of returning a new game. The original permissive `loadState` API remains available to existing callers. Optional appearance and later feature fields retain their established normalization.

`save-storage.js` reads both slots before any write. A valid existing primary seeds a missing/unusable backup without changing primary bytes. Normal writes first capture the prior validated primary in the mode’s `-backup` envelope (format/version/mode/time/raw JSON/FNV-1a checksum), then write the next primary. Unchanged snapshots do not rotate backups. A failed backup write leaves the primary untouched; a failed primary write leaves a usable prior copy. The checksum detects accidental backup changes, not malicious edits. No multi-key transaction is claimed.

Unreadable or missing-with-backup primaries block autosaves; the app displays an exclusive paused recovery view. Explicit replacements recheck the reviewed raw primary and backup before committing. Healthy pre-restore progress becomes an undo backup; damaged primary data never replaces a good backup. Save attempts compare the loaded primary with current storage, and storage events pause a stale tab. This is best-effort conflict protection, not cross-tab transactional synchronization. First-time empty modes can start normally, while retrying recovery after data disappears still requires explicit fresh-start confirmation.

Portrait binaries live separately in IndexedDB. JSON save exports preserve game state but do not contain those image binaries. A new hosting origin starts with separate storage; use reviewed JSON export/import to move progression. Never add automatic uploading of saves without an explicit product decision and privacy review.

## Scene and fitting resources

Mall and wardrobe use the same anatomical rig and merchandise fit rules. Geometry/texture caches share immutable templates; individual actors own skeletons and mutable fitting resources. Pose previews restore the equipped outfit when closed. Scene changes must cancel animation loops and release owned WebGL resources without disposing shared templates.

The character is retargeted from CC0 source geometry. Fabric posing and constrained bag straps are controlled game deformations rather than a complete cloth-physics system. Existing coverage masks and fit tests cover the reviewed motion cases, not every imaginable product/body combination.

## Data and permissions

`product-photos.js` is the runtime index; the older `assets.json` is a retained historical subset. Do not treat the older JSON as the full current catalog. Catalog branch IDs can reuse one real model and photo. `docs/ASSET_INVENTORY.json` records photo provenance and hashes without asserting copyright clearance. Updating a product/photo requires both identity verification and a rights review.

No backend, database credentials or payment integrations are required. The browser fetches local modules/images and remote Google Fonts, and opens external product references only when a player follows a link.

The collection room reuses the studio renderer and the exact owned-product models. Starter sleeves use shared indexed material groups, without duplicating anatomical meshes or modifying the garment fit envelope. Prepared outfits and guestbook pages are bounded optional version-6 save records; applying a planned look validates every purchase before changing equipment. The room and guestbook have no separate backend.

The v27 neighborhood module owns bounded daily notice/property/home records. Validation happens before advancing time or granting XP; activity props never enter purchases. Five local chapters retain the original first three history records. The room studio moves through named furniture-safe paths without changing mall position, and shelf order stays in the existing display ID array. Floor detail uses a disposable 64×64 procedural texture with no external assets.

The v29 `input-controls.js` module owns directional-pad press/release timing and cleanup. Short presses step through the same collision resolver; holds use the existing continuous movement path. Pointer IDs prevent a second finger from ending an active gesture, and cancel/lost-capture/blur/hidden events stop without a step. World keyboard movement requires canvas focus and rejects modified/composing events. Views dispose their pad listeners before replacing DOM. Keyboard focus is revealed above/below fixed navigation without smooth-scroll delays; pointer input keeps its normal scrolling behavior. Dialogs and journey overlays share background inertness, including the skip link; map drawers remain nonmodal with explicit focus return. Responsive controls live beside/below the canvas rather than obscuring it.
